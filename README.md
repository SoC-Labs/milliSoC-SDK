# milliSoC software development kit

Bare-metal SDK for **milliSoC'26**, a dual-core SoC built around an Arm
Cortex-M85, an Arm Cortex-R5 and an Arm Ethos-U85 neural processing unit.

The kit builds a **single flash image** that contains both core images (plus,
optionally, a Vela-compiled NPU model). A small boot loader in the SoC boot ROM
reads that image from QSPI flash, copies each core's code into its own
tightly-coupled memory and starts both cores. Applications are ordinary C
programs: one `main()` per core, `printf()` redirected to a UART, and a
`PASS`/`FAIL` line per check. There is no host-side test framework, simulator
or CI — a "test" is an app that runs on the board and prints its result over
UART.

The toolchain is **Arm DS-6** (`armclang`, `armlink`, `fromelf`); the Makefile
targets `arm-none-eabi` and does not currently build with GCC.

## Hardware at a glance

### Cores and memories

| Memory            | M85 address  | R5 address   | Size      | Use |
| ----------------- | ------------ | ------------ | --------- | --- |
| ITCM / ATCM       | `0x0000_0000` | `0x0000_0000` | 64 KiB (M85), 16 KiB (R5) | Vector table and code. Both images are linked at `0x0`. |
| DTCM              | `0x2000_0000` | —            | 64 KiB    | M85 private data: `.data`, `.bss`, heap and stack. |
| Shared SRAM       | `0x3000_0000` | `0x2000_0000` | 64 KiB    | Data shared by the M85, the R5 and the Ethos-U85 BPU. 64 bits wide, 16 address bits (`A[15:3]` selects one 64-bit word). |
| QSPI XiP window   | `0x6000_0000` | `0x6000_0000` | 4 MiB     | Memory-mapped view of the QSPI flash. |
| Boot ROM          | —             | `0xFFFF_0000` | —        | R5 boot loader generated by `make bootrom`. |
| Debug / trace     | `0xE00F_0000` | `0xE00F_0000` | —        | CoreSight debug APBIC, TPIU (`+0x1000`), ATB funnel (`+0x2000`), R5 ETM (`+0x3000`). |

Notes:

* The **shared SRAM** is one 64 KiB block that each core sees at a different
  address: `0x3000_0000` from the M85 and `0x2000_0000` from the R5. At 64 bits
  wide and 16 address bits it maps as 8,192 double-words. It is the memory the
  Ethos-U85 can reach, so model images, feature maps and DMA buffers live there.
* Because the R5 sees the shared SRAM at `0x2000_0000`, the R5 scatter file
  places that core's `.data`, `.bss`, heap and stacks in shared SRAM, not in a
  private TCM. The two cores' `0x2000_0000` are therefore *different* memories.
* The M85 private DTCM occupies `0x2000_0000`–`0x2000_FFFF`; the linker script
  puts the stack top at `0x2000_FFF0` and reserves 32 KiB for stack plus heap.
* The R5 code must fit in the 16 KiB ATCM: its image is linked at `0x0` and the
  boot loader fills it through the SoC-side alias at `0x8000_0000`. R5 sources
  are compiled `-O0` by default, and the Makefile gives the larger R5 apps
  (`timer_tests`, `mhu_tests`) `-O2` so they do not overflow the ATCM.
* The flash part on the board is an 8 MiB **SST26VF064B** (Pmod SF3), of which
  the current QSPI XiP window exposes 4 MiB (`FLASH_SIZE` in
  `libs/Device/R5/Include/sys_memory_map.h`).

### Peripherals

| Base address | Block |
| ------------ | ----- |
| `0x4000_0000` | CMSDK timer 0 |
| `0x4000_1000` | CMSDK timer 1 |
| `0x4000_2000` | CMSDK dual timer |
| `0x4000_5000` | CMSDK UART 0 (used by `printf` on both cores) |
| `0x4000_6000` | CMSDK UART 1 |
| `0x4000_7000` | Watchdog |
| `0x4000_8000` | RTC |
| `0x4000_9000` | SPI |
| `0x4000_A000` | PL011 UART |
| `0x4001_0000` / `0x4002_0000` | GPIO 0 / GPIO 1 |
| `0x4004_0000`–`0x4005_FFFF` | MHU send (postbox) |
| `0x4006_0000`–`0x4007_FFFF` | MHU receive (mailbox) |
| `0x4400_0000` | AXI DMA controller (ADB400) |
| `0x4401_0000` | QSPI controller |
| `0x4402_0000` | VIC (interrupt controller) |
| `0x4403_0000` | SYSCTRL (core reset/release, boot control) |
| `0x4403_2000` | Ethos-U85 control, queue and PMU registers |
| `0x6000_0000` | QSPI XiP / AHB flash window |

The authoritative table is `libs/Device/R5/Include/sys_memory_map.h` together
with the M85 view in `libs/Device/M85/exectb_mcu/Include/sys_memory_map.h`.

## Repository layout

```
apps/           test/demo applications, one directory per app
                  <app>/<app>_M.c   Cortex-M85 (Thumb)
                  <app>/<app>_R.c   Cortex-R5 (ARM mode)
bootloader/     R5 boot loader; bootrom_gen.py turns its hex into bootrom.sv
libs/
  CMSIS/        CMSIS core and device headers
  Device/M85/   M85 startup, system init and device headers
  Device/R5/    R5 startup and system memory map
  Device/Include/millisoc_platform_m.h, millisoc_platform_r.h
  Drivers/      QSPI, DMA, VIC, MHU and Ethos-U85 register definitions
  common/       retarget (printf over UART) and CMSDK helpers
models/         .tflite sources, Vela config, generated test vectors
scatter/        armlink scatter files (M85, R5, boot ROM)
tools/          concat_hex.py, model_to_image.py, hw_run.py, gen_test_vectors.py
armdbg/         Arm Debugger scripts (flash programmer, boot/reset helpers)
milliSoC/       Arm Debugger (CDB) project and board definition
```

Each app includes `millisoc_platform_m.h` (M85) or `millisoc_platform_r.h`
(R5); those headers are the single entry point for the CMSIS device header,
the memory map, the CMSDK/retarget helpers and the peripheral drivers.

## Getting started

### Prerequisites

* **Arm DS-6** with `armclang`, `armlink` and `fromelf` on `PATH`.
* `make`, plus a Unix-like shell. The recipes use `mkdir -p`, `rm -rf` and
  `cmp`, so on Windows run make from **Git Bash** or the Arm DS shell, not from
  `cmd.exe` or PowerShell.
* **Python 3** for the image tooling.
* Optional, per flow: `jinja2` for `make bootrom`; `vela` (Ethos-U Vela 5.2)
  for `make model`; `pyserial` for the hardware targets (`HW_PYTHON=` selects
  the interpreter that has it).
* A **DSTREAM** for flashing/running on the FPGA board (`armdbg` on `PATH`).

### Build

```sh
make                              # builds the default app, hello
make TESTNAME=mhu_tests           # any directory name under apps/
make clean                        # removes build/
```

Outputs land in `build/<app>/`:

| File | Contents |
| ---- | -------- |
| `<app>.hex` | **The flash image**: 16-byte preamble + M85 image + R5 image (+ optional model). This is what is programmed. |
| `<app>_M.hex`, `<app>_R.hex` | Per-core images, used to build the combined hex. |
| `<app>.bin` | Not the flash image: both core rules write this name and the R5 image wins. Do not flash it. |
| `<app>_M.lst`, `<app>_R.lst` | Disassembly/listing for debugging. |

### Run on the FPGA

```sh
make flash_hw TESTNAME=mhu_tests   # program the image, leave the UARTs alone
make run_hw   TESTNAME=mhu_tests   # program, then capture both UARTs
make uart_hw  TESTNAME=mhu_tests   # capture only (reset the board yourself)
make connect_dstream               # interactive armdbg against the CDB project
```

`run_hw` flashes over DSTREAM, opens both UARTs, prints their output and stops
when the M85 sends the end-of-simulation byte (`0x04`). It returns non-zero if
that marker never arrives or any line contains `FAIL`. Logs are written to
`build/<app>/uart_M85.log`, `uart_R5.log` and `flash.log`.

Defaults on the current bench: M85 on `COM3`, R5 on `COM7`, 250000 baud,
DSTREAM at `192.168.137.59`. Override with `M85_COM=`, `R5_COM=`,
`UART_BAUD=`, `DSTREAM_CONN=`. The COM ports must not be held open by a
terminal.

To run every app in sequence and get a summary table:

```sh
bash tools/run_fpga_regression.sh
bash tools/run_fpga_regression.sh --list
```

## How an image boots

The combined hex starts with a four-word little-endian preamble, then the two
core images:

| Flash offset | Size | Field |
| ------------ | ---- | ----- |
| `0x00` | 4 B | M85 image offset in flash (bytes) |
| `0x04` | 4 B | M85 image size in 32-bit words |
| `0x08` | 4 B | R5 image offset in flash (bytes) |
| `0x0C` | 4 B | R5 image size in 32-bit words |
| `0x10` | … | M85 image |
| … | … | R5 image |
| `0x8000` | … | Optional Vela model image (`APPEND_MODEL=1`) |

Boot sequence, all driven by `bootloader/bootloader.c` running from the boot
ROM on the R5:

1. Initialise the QSPI controller and caches.
2. Read the preamble and DMA-copy the M85 image to `0x0` (ITCM).
3. DMA-copy the R5 image to `0x8000_0000` (the R5 ATCM alias).
4. Hold, reset and release the M85 through SYSCTRL so it starts from the newly
   loaded ITCM.
5. Jump to the R5 application at `0x0`.

Both cores then run their own `main()`. `printf` is retargeted to the CMSDK
UART (`libs/common/retarget`), so a core starts with `UartStdOutInit()`.
`UartEndSimulation()` writes `0x04` and parks in `WFI`; that byte is what the
host capture treats as "test finished". Each core image is padded to a whole
number of 32-bit words and the combined image to a multiple of 16 bytes (four
FIFO words) with `0xFF`, because the flash programmer always clocks a full
16-byte burst and a partial trailing burst does not complete.

`make bootrom` regenerates `bootrom.sv` / `bootrom.bintxt` for the RTL from
the boot loader hex. It needs `SOCLABS_PROJECT_DIR` to point at the RTL project
and writes outside this repository.

## Writing an application

An app is a directory `apps/<name>/` containing `<name>_M.c` and `<name>_R.c`;
the Makefile always builds and links both. Keep the pattern:

```c
#include "millisoc_platform_m.h"     /* millisoc_platform_r.h on the R5 */
#include <stdio.h>

int main(void)
{
    UartStdOutInit();

    printf("M85: %s\n", "my test");
    printf("check %s\n", ok ? "PASS" : "FAIL");

    UartEndSimulation();
}
```

Every check should print `PASS` or `FAIL` (the hardware runner scans for
`FAIL`), and the core that owns the run must call `UartEndSimulation()` when it
is done. A companion file that has nothing to do should still print one banner
line and idle; if the other core owns the run, leave the end marker to it —
see `apps/u85_model/u85_model_R.c`.

Two practical constraints follow from the memory map: the R5 image must stay
inside 16 KiB of ATCM (add `-O2` for that core if `-O0` overflows), and an
image must stay below `MODEL_FLASH_BASE` (`0x008000`) if you want to append a
model to it.

## Applications

| App | What it exercises |
| --- | ----------------- |
| `hello` | Smallest smoke test: UART banners, M85 ETM/ITM trace setup and an R5 ETM APB probe from the M85. |
| `sram_tests` | Shared SRAM stress test on the M85: word, halfword and byte patterns, address-in-address, byte lanes and alignment boundaries (4 KiB window at the SRAM base). The R5 side stays idle because the M85 owns that SRAM during the run. |
| `mhu_tests` | Both MHU-320AE instances: 4 doorbell and 4 fast channels each, polled transport and interrupt delivery, M85↔R5 in both directions. |
| `timer_tests` | CMSDK `TIMER0`, `TIMER1` and `DUALTIMER` on each core, timed with the core cycle counters. |
| `fpu_tests` | Cortex-M85 single-precision FPU: CP10/CP11 enable plus arithmetic, conversion and comparison checks. |
| `debug_access` | CoreSight debug APBIC reachable from each core's system bus: component ID probes from both the M85 and the R5. |
| `bus_access` | Placeholder: prints a banner only. |
| `u85_tests` | Scratchpad for direct Ethos-U85 register pokes (ID, PMU, queue base/size, `BASEP_ARRAY` with hard-coded addresses). |
| `u85_control` | Ethos-U85 control path: ID and soft reset, memory attributes, regions, `BASEP_ARRAY`, a hand-built DMA command stream and repeated launches. |
| `u85_model` | End-to-end ML: reads a Vela model image from flash, checks header and CRC32, runs the command stream on the NPU and verifies every test vector; then benchmarks. |
| `reset_control` | SYSCTRL reset sequencing: CPUWAIT, M85 and R5 local resets, software system reset and watchdog reset, with an MHU handshake across each reboot. Not part of the default regression: it relies on boot-ROM behaviour the current FPGA image does not provide (`--include-reset-control` to try it). |

`bus_access`, `u85_tests` and `sram_tests` are still the least-exercised apps;
`reset_demo` is a legacy single-file demo from before the M85/R5 split and is
not built by the current Makefile.

## Ethos-U85 model flow

`models/` holds the `.tflite` sources, the Vela configuration and the runtime
test vectors. The flow is:

```sh
make model                        # Vela + packer -> build/models/<MODEL>_image.*
make TESTNAME=u85_model APPEND_MODEL=1
make run_hw TESTNAME=u85_model APPEND_MODEL=1
```

| Model | MACs/inference | Weights (flash) | Arena (SRAM) | Runtime image |
| ----- | -------------- | --------------- | ------------ | ------------- |
| `hello_world_int8` (default) | 280 | 1,056 B | 64 B | 1,632 B |
| `micro_speech_int8` | 176,008 | 20,577 B | 14,400 B | 24,673 B |

Vela emits a raw command stream plus a separate weights blob; 
`tools/model_to_image.py` wraps them in a self-describing 96-byte header
(magic `MVL1`, version, offsets/sizes, regions, arena size, CRC32, MAC count).
The image is stored above the code at flash offset `0x008000`, i.e. CPU address
`0x6000_8000`.

`u85_model` is model-agnostic: sizes, arena and MAC count come from the image
header and the vectors from `models/vectors/<MODEL>.h`. The shared SRAM is
laid out as a 32 KiB image window at `0x3000_0000`, a 16 KiB feature-map arena
at `0x3000_8000` and fast scratch at `0x3000_C000`, exactly filling 64 KiB.
`MODEL_RUN_FROM_FLASH=0` (the default) copies the image into SRAM first;
`=1` lets the NPU fetch it from flash once the RTL grants the NPU access to the
QSPI window.

See [`models/README.md`](models/README.md) for the Vela knobs and
[`apps/u85_model/README.md`](apps/u85_model/README.md) for the image format,
memory layout and expected output.

## Tooling

| Tool | Purpose |
| ---- | ------- |
| `tools/concat_hex.py` | Builds the flash image (preamble + M85 + R5 + optional model blob) and applies the 16-byte padding. |
| `tools/model_to_image.py` | Packs Vela raw output into the `MVL1` runtime image and its `.hex`/`.json`/`.h` forms. |
| `tools/gen_test_vectors.py` | Regenerates `models/vectors/<model>.h` by running inputs through the LiteRT integer kernels. |
| `tools/hw_run.py` | Flashes over `armdbg`, captures both UARTs, scans for `FAIL` and the `0x04` end marker. |
| `tools/run_fpga_regression.sh` | Runs every app (or a subset) sequentially and prints a PASS/FAIL summary. |
| `bootloader/bootrom_gen.py` | Converts the boot loader hex into `bootrom.sv` / `bootrom.bintxt` for the RTL. |
| `armdbg/scripts/flash_programmer.py` | QSPI flash programmer driven from the Arm Debugger command view. |

## Current FPGA limitations

These are known silicon/bitstream issues, not SDK bugs:

* **Shared SRAM byte stores.** Unaligned byte writes to shared SRAM commit only
  at 8-byte boundaries, which corrupts byte-oriented data such as model feature
  maps. Work is in progress; word accesses are reliable.
* **M85 and the QSPI controller.** The M85 cannot access the QSPI registers at
  `0x4401_0000`; flash operations run from the R5/boot loader.
* **NPU and the flash window.** The Ethos-U85 currently has no AXI access to
  the QSPI XiP window, so `u85_model` copies the model into SRAM before
  launching (`MODEL_RUN_FROM_FLASH=0`). The direct-from-flash path exists
  behind `MODEL_RUN_FROM_FLASH=1`.
* **`reset_control`** needs boot-ROM behaviour that the current FPGA image does
  not implement, so it is skipped by the default regression run.
